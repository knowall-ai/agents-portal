= Agents Portal Solution Design
:toc: left
:toclevels: 3
:icons: font

== Overview

Agents Portal is a read-only operations portal for the AI agents KnowAll AI builds and runs. It answers three questions for every agent: *Is it up?*, *What can it do?* and *What has it been doing?* — across KnowAll's own tenant and customer tenants.

It persists nothing — there is no database and nothing is written to disk. Everything is read live from Azure, GitHub and Azure AI Foundry using the signed-in user's own permissions, then held in a per-process in-memory cache for a minute (see _Caching_).

== Authentication and Tokens

=== Sign-in

. User clicks *Sign in with Microsoft*
. NextAuth redirects to `https://login.microsoftonline.com/<tenant>/oauth2/v2.0/authorize` — `<tenant>` is `common` by default or the tenant chosen in the tenant switcher
. Requested scopes: `openid profile email offline_access https://management.azure.com/user_impersonation`
. The ARM access token, refresh token and the `tid` claim are stored in the encrypted NextAuth JWT

=== Additional resources

Entra issues one access token per resource. For AI Foundry (`https://ai.azure.com/.default`) and Microsoft Graph (`User.Read`) the server exchanges the refresh token for a resource-specific access token (`src/lib/tokens.ts`). These are cached for five minutes per user.

== Agent Discovery

=== Resource Graph query

One query returns every agent-shaped resource the user can read, across all subscriptions — including subscriptions delegated from other tenants through Azure Lighthouse:

[source]
----
Resources
| where type in~ ('microsoft.compute/virtualmachines', 'microsoft.web/sites',
                  'microsoft.botservice/botservices', 'microsoft.cognitiveservices/accounts',
                  'microsoft.machinelearningservices/workspaces',
                  'microsoft.app/containerapps', 'microsoft.containerinstance/containergroups')
| project id, name, type, kind, location, resourceGroup, subscriptionId, tenantId, tags,
    powerState = tostring(properties.extended.instanceView.powerState.code),
    siteState = tostring(properties.state),
    provisioningState = tostring(properties.provisioningState),
    hostName = tostring(properties.defaultHostName)
----

=== Grouping rules

Resources are grouped into agents by `groupResources()` in `src/lib/agents/discover.ts`:

. A registry entry in `config/agents.json` whose `resourceGroups` contains the resource's group claims it, but only inside the subscriptions in its `subscriptionIds` or, when it names none, the registry's own tenant (`AZURE_AD_TENANT_ID`, or the single tenant in `AZURE_AD_ALLOWED_TENANTS`).
. Otherwise the first tag found from `AGENT_TAG_KEYS` (default `agent`, then `project`) names the agent; the value is slugified (`Zaplie Test` → `zaplie-test`).
. Anything else is ignored.

Registry entries without resources are still listed — as *Planned* when `planned: true`, otherwise *Unknown*.

=== Status derivation

[cols="1,3"]
|===
|Status |Rule

|Online
|All compute resources (VMs, App Services, container apps) are running, or the agent has only managed resources (Bot Service, AI Services)

|Degraded
|Some compute is stopped, *or* compute is running but the agent's `healthUrl` / `portalUrl` did not answer with a 2xx/3xx

|Offline
|All compute is stopped or deallocated

|Planned
|Registry entry with `planned: true` and no resources

|Unknown
|No resources and not planned, or compute state could not be read
|===

The reachability probe uses `redirect: 'manual'`; agent portals behind Entra SSO answer `302` to the login page, which still proves the host is serving.

=== Lighthouse detection

Every Resource Graph row carries `tenantId` — the tenant that owns the resource. When it differs from the tenant in the user's session, the agent is flagged `delegated` and shows a *Lighthouse* badge.

=== Agent identity: avatars and Teams

Each agent card, row and detail header shows a profile image with a status dot. The image comes from where the agent lives, through `GET /api/agents/[id]/avatar`: the Bot Service icon, else the profile photo of the Entra account behind `agent-teams-upn`, read with the user's own tokens and cached for an hour. An `https` `avatarUrl` in the registry or an `agent-avatar` tag overrides it. With none of these the card shows initials on the brand gradient. No pictures live in the repo.

"Chat in Teams" opens a Teams deep link built by `teamsChatUrl()` in `discover.ts`:

[cols="1,3"]
|===
|Agent type |Link

|Has its own Entra account (OpenClaw agents such as Sallie, Pennie)
|`https://teams.microsoft.com/l/chat/0/0?users=<teamsUpn>` — `teamsUpn` from the registry

|Bot Framework / Foundry bot with a Bot Service resource
|`https://teams.microsoft.com/l/chat/0/0?users=28:<Microsoft App ID>` — the app ID is read from the Bot Service's `msaAppId` in Resource Graph
|===

=== Costs

Costs are shown for the current calendar month (month to date) and the previous month, per agent and in total. Amounts stay in each provider's billing currency; nothing is converted, so a total reads "£31.20 · $12.40".

[cols="1,2,2,2"]
|===
|Source |Where it comes from |Attribution |Access needed

|Azure
|Cost Management query API, one call per subscription grouped by resource group and service (`ActualCost`, `MonthToDate` / `TheLastMonth`)
|Rows whose resource group belongs to the agent
|Signed-in user needs *Cost Management Reader* (or Reader/Contributor/Owner) on the subscription. Lighthouse-delegated subscriptions work when the delegation includes that role.

|OpenAI API
|`GET /v1/organization/costs` grouped by `project_id`, using `OPENAI_ADMIN_KEY`
|`openaiProjectId` in the registry
|Server-side admin key

|Anthropic API
|`GET /v1/organizations/cost_report` grouped by `workspace_id`, using `ANTHROPIC_ADMIN_KEY`
|`anthropicWorkspaceId` in the registry
|Server-side admin key

|Subscriptions
|`fixedCosts` in the registry — flat monthly fees invisible to any API (ChatGPT plan, ElevenLabs, Beyond Presence, …)
|Listed on the agent
|None
|===

Billing APIs are rate limited and slow-moving, so results are cached for 30 minutes (failures for 2 minutes). Azure Cost Management additionally throttles third-party client apps to about one query every 25–40 seconds per subscription; queries are therefore serialised through one queue and retried according to the `x-ms-ratelimit-microsoft.costmanagement-*-retry-after` headers. Previous months are requested as an explicit `Custom` time period because the `TheLastMonth` timeframe is rejected by the API. Each source reports a status (`ok`, `not-configured`, `no-mapping`, `error`) which the breakdown shows as a footnote rather than silently omitting a figure. Azure Cost Management lags usage by up to 24 hours.

== Training

The Training tab shows what training an agent has had and what it still owes. The
portal only reads; the training harness owns the records and publishes them to
`knowall-ai/agent-training` (`TRAINING_REPO`), the contract agreed in
https://github.com/knowall-ai/agent-training/issues/14[agent-training#14].

=== Record shape

Runs are one JSON file each, at `runs/<agent-id>/<started_at>-<scenario>[-<run-id>].json`:

[cols="1,3"]
|===
|Field |Meaning

|`result`
|`pass` or `fail`

|`agent`, `scenario`, `started_at`, `mode`, `source`, `run_id`
|Which agent ran which scenario, when, and how

|`operator`
|Who ran it — a name or account, never an email address

|`job`
|`callquality`, `voiceprints` or `handover`: which harness produced the run

|`totals`
|Counters from the harness, e.g. `checks_run`, `actions_verified`

|`questions[]`
|Per-question `check.status` (`pass`/`fail`/`skipped`) and `lag`

|`breaches[]`, `limitations[]`, `change_requests[]`
|What went wrong, what could not be tested, and what should change

|`git`
|Short SHAs of `agent_training`, `agent_presence` and `agent_repo`

|`artefacts`
|`report_md`, `recording`, `transcript` as repo paths or https URLs
|===

The curriculum is `curriculum.yaml` at the repo root: a `scenarios` list of
`id`, `title`, `agents` (the agent ids it is required for) and `cadence`
(`once`, `daily`, `weekly`, `monthly`, `on-change` or `on-demand`).

Every field is optional and unknown fields are ignored, so the harness can add to
the shape without breaking the tab. A run file that is not valid JSON is warned
about and skipped rather than failing the read.

=== Reading and computing

`listTrainingRuns` and `getCurriculum` in `src/lib/providers/github.ts` list
`runs/<agent-id>` and fetch each file (newest first by file name, per-file
failures warned and skipped). The harness commits each agent's runs to its own
`runs/<agent-id>` branch so the code history on the default branch stays clean
and several VMs never race on it; the portal reads that branch first and falls
back to the default branch when it does not exist, while `curriculum.yaml` is
always read from the default branch. The cap is the newest 50 files plus the latest
file of each curriculum scenario that applies to the agent (`selectRunFiles`),
so a one-off induction pass buried under weeks of smoke tests still counts.
GitHub answers 404 both for a missing path and for a private repo the token
cannot read, so a 404 is only treated as "nothing there" after `GET /repos/<repo>`
succeeds; otherwise the tab shows the lookup error. `curriculum.yaml` is parsed
by a small YAML subset parser in `src/lib/training.ts` — the flat shape above
only, including indentless block sequences — rather than adding a YAML
dependency.

`getTraining` in `src/lib/agents/service.ts` composes the two, caches for 10
minutes (a failed read for 1 minute) and returns `configured: false` without
reading anything when the agent has no trusted registry entry: the server's
`GITHUB_TOKEN` is never spent for an agent the caller cannot see. `error` is set
when the repo read fails, so the tab explains itself instead of going blank.

`outstandingFor` marks a scenario outstanding when it has never been run, when
its most recent run failed, or when its last pass is older than the cadence
allows (1 day for `daily`, 7 for `weekly`, 30 for `monthly`; `once`, `on-change` and `on-demand` are
satisfied by any pass, because the portal cannot observe the change that would
make an `on-change` scenario due again).

== Recordings

The Recordings tab (admin-only: recordings are customer meeting content) lets
staff watch a call the agent recorded and read its transcript. Recording is
Teams-native: the agent clicks Teams' own Start/Stop recording, so Teams
announces it, stores the video in the organiser's OneDrive/SharePoint and
produces the transcript. The Presence bridge on the agent VM keeps an index and
serves it at the registry's `recordingsUrl` (contract: agent-presence
`docs/RECORDINGS.md`):

* `GET /recordings?limit&before` — items newest first; `GET /recordings/status`
  — `{active, since, room, id}`; `GET /recordings/{id}` — the item plus
  `turns[{t, speaker|null, text}]`; `GET /recordings/{id}/video` — 302 to
  Teams' short-lived pre-authenticated download URL (409 `{status}` while Teams
  is still producing the file); `GET /recordings/{id}/transcript.vtt` — Teams'
  VTT. Bearer `RECORDINGS_TOKEN` on every route.
* An item is `{v, id (rec_<startedAtCompactUTC>), agent, room, started_at,
  stopped_at, duration_s, status recording|processing|ready|failed, error?,
  meeting{threadId, meetingId, subject, joinUrl}, organizer{name},
  participants[{name}], participant_count, transcript{turns, vtt}, teams{…}}`.
  Names only, never addresses; no VM paths.

The portal never holds Graph application permissions and delegated recording
access only covers meetings the signed-in user organised, so the bridge, which
runs as the agent, is what resolves the media. `src/lib/recordings.ts` parses
the wire shape defensively (a peer service, so nothing is assumed) and drops
any name containing `@`; `src/lib/providers/recordings.ts` talks to the bridge
with `redirect: 'error'` everywhere except the video route, which reads the
302 with `redirect: 'manual'` and only passes an https location on. The portal
routes under `/api/agents/[id]/recordings` sit behind `adminAgentGate`; the
video route answers its own 302 so the browser's `<video>` element streams
straight from Teams with Range support, and nothing is cached (`no-store`).
`recordingsUrl` is a privileged registry field (`entryIsPrivileged`), so the
entry must pin `subscriptionIds`.

== Caching

`src/lib/cache.ts` is a per-process TTL cache keyed by tenant and user for anything read with the user's token, so users never see each other's data; agent-global facts read with server tokens (Boost state, brain snapshots, repo skills, provider cost reports) are keyed by agent alone. Defaults: 60 s for Azure lookups (`CACHE_TTL_SECONDS`), 10 min for skills, 5 min for exchanged tokens. The UI polls agents every 60 s and activity every 2 min.

== Security Considerations

* The dashboard never holds credentials with more access than the signed-in user; Azure RBAC decides what is visible.
* Access and refresh tokens stay inside the encrypted NextAuth JWT cookie and are only read server-side (`getUserContext`); the session object sent to the browser carries no tokens.
* The server-held secrets are the Entra client secret, `GITHUB_TOKEN` (Contents: read only), `REVERIE_TOKEN` (sent only to the registry's `brainUrl`), `RECORDINGS_TOKEN` (sent only to the registry's `recordingsUrl`) and the optional provider admin keys `OPENAI_ADMIN_KEY` and `ANTHROPIC_ADMIN_KEY` used for the cost reports. Everything else is read with the signed-in user's own token.
* Sign-in is refused unless the user's tenant is on the `AZURE_AD_ALLOWED_TENANTS` allow-list, which a production deployment must set: with the multi-tenant authority `common` and no list there is nothing to check against, so no one is admitted.
* A registry entry only applies to an agent when the caller can see one of its Azure resources inside the scope the entry claims — the subscriptions in its `subscriptionIds`, or the registry's own tenant — so a same-named resource group elsewhere cannot inherit its brain URL, repo or boost script.
* Values that originate from Azure resource tags are untrusted because anyone with Contributor on a resource can set them:
** `agent-url` / `portalUrl` must be `https`, and the reachability probe refuses hosts that resolve to loopback, link-local (including the 169.254.169.254 metadata endpoint) or private ranges. Response bodies are never read.
** `agent-repo` / `repo` must match `owner/name` before it is placed in a GitHub API path.
** `agent-avatar` / `avatarUrl` must be a same-origin path or an `https` URL.
* The Activity Log OData filter escapes quotes in resource group names.
* Every response carries HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a referrer policy and a permissions policy; the `X-Powered-By` header is disabled.
* Tokens are never logged; NextAuth logging is redacted.
* The tenant cookie is `httpOnly`, `sameSite=lax`, validated against a GUID pattern.
* Hosting: HTTPS only, TLS 1.2 minimum, FTPS disabled, App Service managed certificate.

See `SECURITY.md` for the reporting policy.
