= Onboarding an Agent
:toc: left
:icons: font

This guide explains how to make an agent appear in Agents Portal — whether it runs in KnowAll's tenant or in a customer's.

== 1. Tag the Azure resources

The quickest route needs no code change. Tag every resource that makes up the agent (VM, App Service, Function App, Bot Service, AI Services account) with `agent=<slug>`:

[source,bash]
----
# Example: Winnie's dev resource group in the KnowAll tenant
az tag update --operation merge --resource-id \
  $(az group show -n rg-winnie-dev --query id -o tsv) \
  --tags agent=winnie agent-customer="Irish FA" agent-kind=foundry environment=dev

# Tags on a resource group are NOT inherited — apply them to the resources too
for id in $(az resource list -g rg-winnie-dev --query '[].id' -o tsv); do
  az tag update --operation merge --resource-id "$id" \
    --tags agent=winnie agent-customer="Irish FA" agent-kind=foundry environment=dev
done
----

Optional tags:

[cols="1,3"]
|===
|Tag |Purpose

|`agent`
|Slug that groups resources into one agent (required unless the registry claims the resource group)

|`agent-customer`
|Customer name shown on the card (default *Unassigned*)

|`agent-kind`
|`openclaw`, `foundry` or `botframework` (otherwise inferred from resource types)

|`agent-url`
|Portal URL to link to and probe for reachability

|`agent-repo`
|GitHub repo (`owner/name`) for commit activity

|`agent-description`
|One-line description

|`agent-avatar`
|Profile image override — an `https` URL. Usually unset: the portal shows the Bot Service icon or the Entra account photo

|`agent-openai-project`
|OpenAI project id (`proj_…`) whose API spend belongs to this agent (Costs tab). Create one project per agent and issue the agent's API key inside it

|`agent-anthropic-workspace`
|Anthropic workspace id (`wrkspc_…`) whose API spend belongs to this agent

|`environment`
|`prod`, `test` or `dev`
|===

TIP: Deployments made with `azd` already carry a `project` tag. Because `AGENT_TAG_KEYS` defaults to `agent,project`, those agents are discovered without extra tagging — that is how Winnie (`project=winnie`) and Pennie (`Project=Pennie`) appear today.

== 2. Or add a registry entry

For richer metadata (skills repo, portal URL, health URL) or for resources you cannot tag, add an entry to `config/agents.json`:

[source,json]
----
{
  "id": "sallie",
  "name": "Sallie",
  "kind": "openclaw",
  "customer": "KnowAll AI",
  "environment": "prod",
  "description": "AI sales agent — Teams, email and voice.",
  "portalUrl": "https://sallie.knowall.ai",
  "healthUrl": "https://sallie.knowall.ai/health",
  "repo": "knowall-ai/sallie-openclaw",
  "skillsPath": ".claude/skills",
  "skillSources": [
    { "repo": "knowall-ai/claude-plugins", "path": "skills" },
    { "repo": "T-Minus-15/claude-plugins", "path": "skills" }
  ],
  "resourceGroups": ["ka-agents"]
}
----

* `resourceGroups` claims every agent-shaped resource in those groups, tagged or not — but only inside the scope the entry is trusted for: the subscriptions listed in `subscriptionIds`, or, when it lists none, the registry's own tenant (`AZURE_AD_TENANT_ID`, or the single tenant in `AZURE_AD_ALLOWED_TENANTS`). Resource-group names are only unique within a subscription, so an entry that claims groups in another tenant — a Lighthouse-delegated subscription, say — must set `subscriptionIds`, otherwise it claims nothing.
* `skillsPath` is the folder containing `<skill>/SKILL.md`; symlinks (e.g. `workspace/skills → ../.claude/skills`) are followed.
* `skillSources` lists shared skill packs the agent also loads at runtime (for OpenClaw, the repos in `skills.load.extraDirs`). A skill in the agent's own repo shadows a same-named plugin skill, exactly as it does at runtime. `GITHUB_TOKEN` must be able to read these repos too.
* `appRegistrations` lists the Entra app registrations the agent runs as (`appId` + `label`). The *Permissions* card shows each one's API permissions with Microsoft's description and whether the tenant has consented, plus the account's directory roles, groups and Azure RBAC roles. Bot Service app IDs are added automatically.
* `brainUrl` enables the *Brain* tab: the base URL of the agent's `reverie serve` behind its reverse proxy (e.g. `https://sallie.knowall.ai/reverie`). The portal sends `REVERIE_TOKEN` to it, so only registry URLs are used, never tags.
* `boost` enables the *Boost* card: `script` is the absolute path of the agent's `boost.sh` on its VM (`on <hours>` / `off` / `status`, prints one JSON line), `defaultHours` and `maxHours` bound the duration. The VM reverts on its own via a systemd timer, so a forgotten Boost never outlives its window. Viewers need Virtual Machine Contributor on the VM to use it.
* `soulPath` points at the agent's `SOUL.md`; leave it out for the OpenClaw default (`workspace/SOUL.md`, then `SOUL.md`). It renders on the agent page.
* Agents appear automatically once their Azure resources are tagged — a registry entry is only needed for metadata. Set `"planned": true` only when you deliberately want an agent listed before anything is deployed.
* `avatarUrl` is an override only (an `https` URL). Leave it unset so the picture comes from the Bot Service icon or the Entra account photo.
* The agent's own Entra account comes from the `agent-teams-upn` tag on any of its Azure resources (`az resource update --ids <resource-id> --set tags.agent-teams-upn=<agent>@<tenant-domain>`); `teamsUpn` in the registry overrides it but should stay unused, because this repo is public and must not carry addresses. It powers the *Chat in Teams* button and the *Licences* card (account state and Microsoft licences read from Graph). `fixedCosts` entries are listed there too as subscriptions. Bots do not need it — their Bot Service app ID is used instead.
* Registry values override tag values.

Private repos need `GITHUB_TOKEN` set on the server (fine-grained token, Contents: read).

== 3. Customer tenants: Azure Lighthouse

When an agent is deployed in a *customer's* Azure subscription, delegate it to KnowAll with Azure Lighthouse so it appears for KnowAll users without switching tenant.

. In the KnowAll tenant, create a security group for dashboard readers and note its object ID.
. Ask the customer to deploy a Lighthouse delegation that grants that group the *Reader* role on the agent's subscription or resource group. The Azure portal wizard is at *Service providers → Service provider offers* (customer side) or use an ARM template:
+
[source,bash]
----
az deployment sub create --location uksouth \
  --template-uri https://raw.githubusercontent.com/Azure/Azure-Lighthouse-samples/master/templates/delegated-resource-management/subscription/subscription.json \
  --parameters mspOfferName="KnowAll AI Agent Monitoring" \
               managedByTenantId=<knowall-tenant-id> \
               authorizations='[{"principalId":"<reader-group-object-id>","principalIdDisplayName":"KnowAll agents portal readers","roleDefinitionId":"acdd72a7-3385-48ef-bd42-f606fba81ae7"}]'
----
. Sign in to Agents Portal with the KnowAll tenant. The customer's agents appear with a *Lighthouse* badge.

*Reader* is enough for status, resources and the Activity Log. To list the customer's AI Foundry assistants and runs, the group also needs *Azure AI User* on the AI Services account.

NOTE: Lighthouse delegates Azure resources only. Anything read through Microsoft Graph (Teams presence, mailboxes) stays inside the customer's tenant.

== 4. Customer tenants: signing in directly

A user with an account in the customer's tenant (their own staff, or a KnowAll guest user) can sign in to that tenant instead:

. A tenant admin grants consent once: `https://login.microsoftonline.com/common/adminconsent?client_id=<AZURE_AD_CLIENT_ID>`
. In the dashboard header, open the tenant switcher and pick the customer tenant. Sign-in re-runs against that tenant and the agent list is scoped to it.

== 5. Exposing a health endpoint (OpenClaw agents)

The dashboard probes `healthUrl` (or `portalUrl`) and accepts any 2xx/3xx. A portal behind Entra SSO already answers `302`, which counts as reachable. For a real health signal, expose the OpenClaw gateway's `/health` without SSO in Caddy:

[source]
----
handle /health {
    reverse_proxy localhost:3000
}
----

and set `healthUrl` to `https://<agent>.knowall.ai/health`.

== 6. Profile image and Teams chat

* *OpenClaw agents* usually have their own Entra user. Upload a photo to that account (`az rest --method put --url 'https://graph.microsoft.com/v1.0/users/<upn>/photo/$value' --headers 'Content-Type=image/jpeg' --body @photo.jpg`; Graph requires the JPEG content type, and `az rest` does not set it for a non-JSON body) and tag a resource with `agent-teams-upn`; the portal reads the photo from there.
* *Bot Service agents* get their picture from the bot's icon: Azure portal → the Bot Service resource → *Bot profile* → *Icon*.
* *Bots* get a Teams link automatically from their Bot Service resource, provided the bot has the Teams channel enabled and the user has the app installed.

== 7. Costs

Azure costs need no setup beyond the user having *Cost Management Reader* on the subscription. To attribute LLM API spend and flat fees:

[source,json]
----
{
  "id": "sallie",
  "openaiProjectId": "proj_xxxxxxxx",
  "anthropicWorkspaceId": "wrkspc_xxxxxxxx",
  "fixedCosts": [
    { "label": "ChatGPT subscription", "amount": 200, "currency": "USD" },
    { "label": "ElevenLabs Creator", "amount": 22, "currency": "USD" }
  ]
}
----

* Find the OpenAI project id under *Settings → Organization → Projects*; the Anthropic workspace id under *Settings → Workspaces*.
* Set `OPENAI_ADMIN_KEY` / `ANTHROPIC_ADMIN_KEY` on the server (organisation admin keys, read-only use). Without them the breakdown says "not configured" rather than showing zero.
* Give each agent its own OpenAI project / Anthropic workspace, otherwise spend cannot be separated.

== Giving a customer access

See link:CUSTOMER-ACCESS.adoc[Customer access]: invite them as a guest, grant `Reader` on their agent's resource group, assign the `Portal.Viewer` app role. Nothing in the registry changes.

== Checklist

* [ ] Resources tagged `agent=<slug>` *or* resource group listed in `config/agents.json`
* [ ] `agent-customer` / `customer` set
* [ ] `environment` set
* [ ] Portal / health URL set
* [ ] GitHub repo and `skillsPath` set (OpenClaw agents); `skillSources` if the agent loads shared skill packs; `SOUL.md` in the repo if you want the Soul card
* [ ] `avatarUrl` set and, for agents with their own account, the `agent-teams-upn` tag on a resource
* [ ] `agent-openai-project` / `agent-anthropic-workspace` tags (or the registry ids) and `fixedCosts` set so the cost breakdown is complete
* [ ] `brainUrl` set for agents running `reverie serve`, and `REVERIE_TOKEN` set on the server (never `BRAIN_FIXTURE=1` outside development)
* [ ] Lighthouse delegation in place (customer-hosted agents)
